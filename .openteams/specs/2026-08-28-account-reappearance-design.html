账号重新出现状态修复

修复账号已重新出现在 sub2api 列表中，但面板仍保留“已移除”运行状态的问题，同时保留用户已有的自动化策略。

问题位置库存 upsert 保留了旧的 runtime_state=missing
恢复原则同一身份重新出现时保留启用策略
安全边界身份变化时仍强制关闭自动化

已确认的原因

sub2api 的筛选接口当前返回全部 8 个 OpenAI OAuth 账号。库存同步也会将匹配记录的 missing 字段恢复为 0，但对可调度账号沿用了同步前的 runtime_state。如果旧状态为 missing，面板状态徽标就会继续显示“已移除”。

不可调度账号没有暴露这个问题，因为既有分支会把它们直接改为 paused。这与现场截图中 3 个不可调度账号显示“已暂停”、5 个可调度账号显示“已移除”的组合完全一致。

方案选择

方案处理结论
后端状态恢复upsert 时识别“原来缺失、现在重新出现”，结合原策略恢复状态和预检计划。采用。同时修复显示和调度。
仅修正前端标签根据 missing 字段覆盖徽标文字。不采用。后台仍停留在错误状态。
所有重新出现账号立即检查不区分策略是否启用，统一进入待检查。不采用。未启用账号会显示误导状态。

状态迁移

重新出现时的条件策略目标状态下一动作
身份未变化，账号符合调度条件已启用pending_check将 next_action_at 设为当前时间，立即执行只读 quota 预检。
身份未变化，账号符合调度条件未启用disabled保持无下一动作，不访问 quota。
身份未变化，但账号不符合调度条件任意paused清空下一动作，显示具体不可调度原因。
OpenAI 身份哈希发生变化原来已启用identity_changed关闭策略、终止旧周期并要求管理员重新启用。

账号重新出现不等于身份替换。只有远端 ID、创建时间和 OpenAI 身份仍匹配时才允许保留原策略；现有身份保护规则不放宽。

数据流

1. 列表同步
先将当前连接库存标记为缺失，再读取本次完整账号列表。
→
2. 匹配与恢复
按连接、远端 ID 和创建时间匹配，识别旧记录是否处于缺失状态。
→
3. 策略感知
已启用账号进入只读预检；未启用账号恢复为关闭；身份变化继续锁定。

整个修复不增加远端写调用。重新出现且已启用的账号首先读取 quota，只有既有调度规则判定到期后才可能发送一次 hi。

实现边界

  • 只修改库存恢复逻辑及对应测试，不改 sub2api 客户端、页面接口或数据库结构。
  • 状态恢复在同一个 SQLite 事务中完成，避免页面看到 missing=0 但运行状态仍为 missing 的中间状态。
  • 使用现有 account_policies.enabled 判断是否安排预检，不创建新的配置项。
  • 普通同步中的非缺失账号维持原状态和下一动作，防止每次同步都重置已有周期。

测试与验收

  1. 先同步一个符合条件且策略已启用的账号，再用空列表将其标记缺失，最后重新同步同一身份；断言策略仍启用、状态为 pending_check、下一动作已到期。
  2. 同样流程用于未启用账号；断言状态为 disabled 且没有下一动作。
  3. 重新出现的账号不可调度；断言状态为 paused，没有下一动作，并保留原因。
  4. 账号重新出现但身份哈希变化；断言策略被关闭、身份代次增加、旧周期被终止。
  5. 连续同步从未缺失的账号；断言现有运行状态和下一动作不被重置。
  6. 通过 Go 格式检查、单测、race 和现有 GitHub Actions 后发布补丁版本。
