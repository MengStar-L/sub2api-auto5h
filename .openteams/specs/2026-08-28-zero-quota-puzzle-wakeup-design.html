已确认的问题

OpenAI usage 返回的 5h 窗口可能同时包含 used_percent=0 和未来 reset_at。sub2api 只转发 usage 数据，并在管理面板中明确将 OpenAI OAuth 的 0% 用量显示为“现在”。因此，未来时间本身不能证明窗口已经启动。

当前 auto5h 的 FiveActive 只检查 reset_at > now，会把查询产生的“当前时间 + 5h”误当成活动窗口；同一个错误还存在于外部激活识别、失败请求后的成功推断和成功请求后的额度验证中。

只比较 reset 时间会产生假阳性：请求没有真正激活，程序却可能记录为外部已激活、推断成功或验证成功。所有这些位置必须同时使用 5h 用量。

参考实现结论

cockpit-tools 的官方直连唤醒会向 Responses 流式接口发送真实问题，默认提示词为 hi，并要求得到可读回复；其额度重置调度器每 30 秒检查已保存的重置时间。

该项目当前没有在唤醒成功后比较 quota，并存在“任务显示成功但未开启 5h 窗口”的记录。本项目借鉴“发送真实问题并读取回复”，但继续采用更严格的 SSE 终态和后置 quota 验证，不把可读回复单独当作额度已验证的证据。

“激活是否成功”和“答案是否正常”是两个正交状态。错误答案不会写入 last_error、不会暂停账号，也不会触发同周期重试。

后置额度协调

  • 显式 SSE 成功后仍在 10、30、60 秒读取 quota。
  • 只有 5h used_percent > 0 且未来 reset 合理时，才标记 verified 并创建下一 reset 周期。
  • 如果 quota 保持 0%，周期维持 success_unverified，下一动作按请求接受时间 + 5h + 延迟推算，到期前仍重新预检。
  • 请求错误或超时后的协调也必须看到 used_percent > 0，才允许标记 inferred_success；单独的 reset 前移不再足够。
  • 一旦 SSE 明确成功，无论答题结果或验证结果如何，本周期都不重发。

测试与验收

  1. 0% + 未来 5h reset 被判定为空闲并立即执行；刷新 quota 后不再显示“等待刷新”。
  2. 大于 0% + 未来 reset 继续等待；新的活动窗口才能记为外部已激活。
  3. 失败请求后的 quota 仍为 0% 且 reset 前移，不得推断成功。
  4. 显式成功后的 quota 仍为 0%，保持 success_unverified 且不重发；大于 0% 时才验证成功。
  5. 测试请求体包含完整固定题目、只返回数字的约束、配置模型和 mode=default。
  6. SSE 分片回复拼接为 21 时标记正常；其他数字、说明文字和空回复均标记不正常，但激活成功且不重试。
  7. 缺少成功终态、错误事件、超时和超限响应仍按原安全策略处理，不写入新的答题结果。
  8. SQLite 从旧数据库自动迁移，历史数据保持可读；账号列表、抽屉和尝试 API 返回新增字段。
  9. 前端在 1440×900 和 390×844 下展示状态及回复，无溢出、遮挡或错误的 SPA 回退。
  10. 只在 GitHub Actions 执行 Go/Vue 编译、单测、race 和 Playwright；全部通过后发布新的补丁版本。
